## 2. Why the opening did not feel cinematic

1. **The photo sat in a bordered card.** A framed image reads as UI, not as a world you can enter. The zoom therefore looked like "enlarge the card" rather than "camera moves into the room".
2. **The IDE left the screen.** After filling the frame it shrank into a side window. That contradicts the story: once you are inside the display, the display *is* the world.
3. **Photo mapping assumed the frame had the photo's exact aspect.** Any editorial crop (`object-fit: cover`) would have broken the screen-corner tracking, which forced the card layout.
4. **Hero copy competed with the shot.** Two primary actions and a long description sat over the start of the zoom on mobile.
5. **Chapter navigation vanished below 800 px**, so tablet and mobile users (and the two tests) had no chapter controls.

## 3. Rendering technique for the opening (recommended and implemented)

**2.5D photographic dolly + tracked homography hand-off to live DOM**, not Blender, for Shots 1–4:

- The single photograph only supports a camera moving *toward* it (scale about a fixed point). We never fake parallax or new viewpoints from it.
- The four display corners are measured in source-image pixels and mapped through the real `object-fit: cover` / `object-position` maths, so the photo can be cropped editorially on any viewport and the corners still land exactly.
- A real HTML editor is warped onto those four corners every frame (`matrix3d` homography), crossfades over the photographed pixels while still small, straightens as the camera arrives, and ends as a full-bleed, crisp, selectable-quality interface. Text is never an upscaled bitmap.
- Blender is the right tool from Shot 5 onward (Git → build → deployment), where the camera must travel through space the photo cannot provide.

## 5. Single master scroll and camera architecture

```
native scroll
   └─ one GSAP ScrollTrigger (dynamically imported, start 0 → end max)
        └─ chapter-aware progress t = i + local   (from measured DOM section anchors)
             └─ SCENES[] — pure functions seek(t) → styles / camera / packet
                  ├─ photo dolly + display homography      (DOM)
                  ├─ editor hold, pulse                     (DOM)
                  ├─ packet                                  (DOM ↔ WebGL via journeyPath.projectSignal)
                  ├─ image-sequence player                   (canvas 2D, Milestone 2+)
                  └─ R3F camera + signal                     (frameloop "demand", invalidated per update)
```

- `t` is the only state. Every scene computes its output from `t` alone, so fast scrolls, reversals, chapter jumps, resizes and session restores all land on the same frame.
- No scene owns a ScrollTrigger, timer or tween. Nothing renders while the scroll is idle (measured: 0 draw calls in 1.5 s).
- Image sequences (Milestone 2+) are mapped as `frame = round(local × (n − 1))`, with a ring buffer of decoded `ImageBitmap`s around the current frame, a poster frame per scene, and network-aware preloading of the next scene only.

## 7. Shot plan — first 10–15 seconds

Timing assumes a steady trackpad scroll (~170 px/s). `t` is chapter progress.

| Shot | t | ≈ s | Camera / picture | What it means |
| --- | --- | --- | --- | --- |
| 1 Establishing | 0.00–0.04 | 0–1 | Your photograph full-height on the right, bleeding into the dark stage; headline left | A real developer at a real desk |
| 2 Approach | 0.04–0.30 | 1–6 | Slow dolly toward the display about a fixed point; hero copy recedes; the display starts emitting a cyan glow as the live editor fades in **inside the four measured corners** | Attention moves from the person to the work |
| 3 Cross the bezel | 0.30–0.56 | 6–10 | Display perspective straightens; the room dissolves into the dark stage; the editor fills the frame edge to edge | The screen becomes the world |
| 4 Inside the source | 0.56–1.05 | 10–14 | Full-bleed editor, very slow push-in toward `BooksController.Search`; the chapter caption appears lower-left | A request handler is written |
| 5 The pulse | 1.00–1.15 | 14–15 | A light pulse rings `service.SearchAsync(query)` | This call is the object we follow |
| 6 Lift-off (existing) | 1.15–1.80 | 15–18 | The token lifts out, the editor recedes, the packet hands off to the 3D signal | Code leaves the editor for source control (Milestone 2 replaces the placeholder world) |

## 9. Milestone 2 — engineering infrastructure (Git → build/test → deployment)

**Preview:** `/code-to-experience`, scroll past the editor (t ≈ 1.5 → 3.95).

**What is on screen.** The camera pushes through the editor into one continuous rendered space, following the same packet:
1. **Git bay:** the packet leaves `main` on `feature/library-search`, passes commits `a3f9c21` and `7be104d`, merges, and goes through the `release/v1.0` tag gate.
2. **CI hall:** it rides a conveyor through machined stations — `RESTORE` (`dotnet restore`, package crates), `BUILD` (`dotnet build -c Release`, compiler vents), `TEST` (`dotnet test`, status board) and `PACKAGE` (`dotnet publish`). There it picks up a glass release-artifact crate.
3. **Deployment corridor:** a cold-aisle data-centre corridor (server faceplates with status LEDs, fibre trays, ceiling panels), ending as the artifact slides into a `PRODUCTION · HEALTHY` rack.

Commit hashes, commands and success lamps are illustrative, as the chapter notes say. They are not this repository's real CI output.

**Technologies**

| Tool | Status | Purpose |
| --- | --- | --- |
| Blender 4.5.10 LTS (winget `BlenderFoundation.Blender.LTS.4.5`) | New local tool (not an npm dependency) | Procedural scene, Eevee renders |
| ffmpeg 9.0.1 (winget `Gyan.FFmpeg.Essentials`) | New local tool | Review videos (MP4) |

| GSAP ScrollTrigger | Existing | Still the single director; the sequence is one more scene of it |

No npm dependencies were added. Fonts (Cascadia Mono, Segoe UI) are Windows system fonts. They appear only as rendered pixels; no font files are shipped.

**Reproducible pipeline**
```
blender -b --factory-startup -P blender/scripts/pipeline_scene.py -- --variant desktop --mode render
blender -b --factory-startup -P blender/scripts/pipeline_scene.py -- --variant mobile  --mode render
node Scripts/encode-cinematic.cjs pipeline 68
```
- `pipeline_scene.py` builds geometry, materials (brushed metal, polished tiles, glass, procedural server LEDs), lights, the camera path and the packet path in code, so there is no opaque `.blend` to trust. `--mode save` writes an inspectable `.blend`.
- Desktop: 240 frames at 1280 × 720, landscape lens. Mobile: 240 frames at 540 × 960, its own portrait framing. Eevee with 32 samples took 16 + 12 minutes on this laptop.
- Output in `public/cinematic/pipeline/{desktop,mobile}/`: `NNNN.webp`, `poster.webp`, `manifest.json`. Desktop is 8.7 MB (37 KB/frame), mobile 4.5 MB (19 KB/frame).

**Synchronisation with the master timeline**
- The manifest stores `tStart = 1.5`, `tEnd = 3.95`, and for every frame the packet's projected screen position (`world_to_camera_view` from Blender's own camera).
- `pipeline.js` → `frame = round((t − tStart) / (tEnd − tStart) × 239)`, drawn with object-fit: cover. The packet position is mapped through the same cover transform.
- The live DOM packet from the opening flies to that exported position, then fades over t 1.70–1.80 onto the rendered packet. Rewinding reverses the hand-off exactly.
- Loading: nothing is downloaded before t > 0.5, never under reduced motion, and the right variant is picked per viewport. Keyframes come first (every 32nd, 16th … frame), with at most 6 concurrent fetches. At most 18 decoded `ImageBitmap`s are kept around the current frame; the nearest decoded frame is shown until the exact one is ready.

**Evidence**
- Frames: `artifacts/code-to-experience-transition/milestone2/` (desktop, tablet, mobile; t 1.3 → 4.1).
- Recordings (t 0 → 4 → 0): `artifacts/code-to-experience-transition/recording/*.mp4`.
- Tests: full suite 141/141. New checks: the drawn frame equals the frame for the director's own reported progress, at three positions on every viewport; the live packet is within 5% of viewport width of the rendered packet at the hand-off; the sequence hides again on rewind; reduced motion makes zero `/cinematic/` requests.

| --- | --- | --- | --- |
| Desktop, final build | 16.8 ms | 6–8 (earlier near-identical builds: 19–36) | 0 |

  Fixed along the way, all measured:
  - Full-page React re-renders on every chapter change re-reconciled the whole WebGL world (0.2–0.6 s long tasks at chapter boundaries). Chapter content and the world are now memoised.
  - The hidden WebGL world kept rendering under the footage. It now renders only while visible.

  - A packet hand-off regression introduced by the editor-hiding optimisation; caught by the new test.

**Known limitations**
- Eevee, not Cycles; procedural assets, not authored GLB/PBR textures. It reads as a believable data centre and CI hall, but it is not film-grade. A Cycles pass of the same script is the natural upgrade (expect about 10× the render time).
- At t ≈ 4 the footage hands over to the old placeholder WebGL world. Milestone 3 replaces that (backend → database → response).
- The rendered packet and the live packet differ slightly in shape (icosphere vs. DOM diamond). The cross-fade hides it, but it is visible if you pause at t ≈ 1.75.
- The 13 MB of frames are now in `public/`. They are committed only if you approve a commit.

## 10. Performance implications

- The opening is DOM/compositor work with one 88 KB image. The cost is raster, not JavaScript (traced: 0 long tasks).
- A full-bleed homography editor re-rasterises as it scales. Sizing the editor's base box to its final full-bleed rect makes the resting state 1:1 (crisp, no re-raster while idle).
- Image sequences are the main future cost. Budget per scene: desktop ≤ 6 MB, mobile ≤ 2.5 MB AVIF, streamed scene by scene. Nothing loads before the visitor reaches that chapter's neighbour.
- WebGL stays `frameloop="demand"`. Chrome on this laptop renders on the Intel GPU by default, and real visitors will too, so that is the profiling baseline. The RTX 3050 is a best-case reference only.

**Pipeline**

- Render: Blender 4.5.10 LTS, Eevee Next with ray tracing, 32 samples. Desktop: 288 frames at 1280 × 720. Mobile: 288 frames at 540 × 960 with its own lens and shift. On this laptop, desktop took ≈ 1.5–4.7 s per frame and the whole job took ≈ 20 minutes. Previews (8–16 samples, 50%) took ≈ 1 s per frame.
- Encode: WebP q68. Desktop 8.1 MB (29 KB per frame), mobile 4.7 MB (17 KB per frame). `manifest.json` carries the per-frame artifact projection, radius, beats and hand-off.
- `Scripts/job-runner.cjs` (local tool, started by hand) runs only named jobs from `artifacts/jobs/queue/` (Blender preview/render/export, encode, lint, build, Playwright, capture, record, profile, dev/prod server, sysinfo). It runs them one at a time because RAM is limited.
- Low-RAM findings: Blender crashed until the dev server was stopped. Complex node graphs failed to compile in the NVIDIA driver, so the display-layer shaders were rebuilt from about 25 nodes to 5–6, and shader compilation is limited to one worker.
